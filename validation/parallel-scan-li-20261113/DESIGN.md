# 设计：并行精确扫描（Parallel exact scan）

日期：2026-11-13　分支：`perf/self-iterate-li-20261113`（工作区未提交）
证据目录：`/home/li/verify-out-20261113/`

## 1. 目标与不变量

**目标**：在不改变任何可观察语义的前提下，把单次精确 TopK 查询的墙钟时间降下来，
从而抬高加赛性能分（查询权重为写入的 2 倍）。

**必须保持的不变量**：

1. 结果逐字节一致——相同行、相同顺序、相同距离值（FP64 累加不变）。
2. 距离并列仍按主键升序（原有 total order）。
3. 过滤、投影、LIMIT、点查、事务可见性、持久化、恢复语义不变。
4. 峰值内存不显著上升（评分中内存占 20%）。
5. 单 CPU 环境下不得比串行更慢。

## 2. 依据（本机实测）

10k×128D、10000 次查询的 `perf` 采样（RelWithDebInfo）：

| 符号 | 占比 |
| --- | ---: |
| `quantized_squared_distance_avx2` | 36.7% |
| `Compact::distance_cell` | 19.9% |
| `execute_statement`（解析/规划/分发） | 14.0% |
| 其余 | ≤3.4% |

即约 **57% 的查询时间是可并行的距离计算**，且是 compute-bound。

微基准（真实内核 `quantized_squared_distance_avx2`，10000 行 × 128 维 × 10000 查询）：

```
1 线程 1451.6 ms → 2 线程 721.4 ms（2.01×）→ 4 线程 388.0 ms（3.74×）
```

校验和三次一致，说明没有内存带宽瓶颈。

官方 checker 默认配置为 2 CPU（`PROTOCOL_IMPLEMENTATION.md`），团队 A/B 也用
`AllowedCPUs=0-1`、`CPUQuota=200%`。因此 2 个扫描 worker 是目标配置。

## 3. 架构

```
                     ┌──────────────┐
   execute(query) ──▶│ scan_width() │──▶ 1（串行，原路径）
                     └──────┬───────┘
                            │ ≥2
                     ┌──────▼───────────────┐
                     │ run_slices(total, f) │
                     └──────┬───────────────┘
         ┌──────────────────┼──────────────────┐
         ▼                  ▼                  ▼
   slice 0 (main)     slice 1 (worker)   slice k …
   local Heap(0)      local Heap(1)      local Heap(k)
         └──────────────────┼──────────────────┘
                            ▼
                  按 (distance, key) 合并到 nearest
```

**单元职责**

| 单元 | 职责 | 依赖 |
| --- | --- | --- |
| `WorkerPool` | 进程级固定线程池，一次查询一次 fork-join；捕获 worker 内异常回传主线程 | `<thread>`/`<mutex>` |
| `usable_cpus()` | 读 `sched_getaffinity`，得到本进程真实可用 CPU 数 | `<sched.h>` |
| `scan_width(rows)` | 决定本次查询宽度：`thread_limit()` 覆盖 > 亲和性 > 上限 4；行数 < 1024 或宽度 < 2 时返回 1 | 上面两者 |
| `scan_contiguous` | 连续 row 区间的原扫描逻辑（8/32 批 + 量化筛选） | `exact::Compact` 只读 |
| `scan_list` | 候选行列表（postings 或预过滤结果）的 32 行批扫描 | 同上 |
| `run_slices` | 切分、并行、合并、计数 | 上面全部 |

**并行只在查询内发生**。语句执行本身就是串行的（JSONL 一次一条），因此不需要任何
语句间同步；写入路径不创建线程。

## 4. 正确性论证

- 合并比较器 `better_neighbor` 是 `(distance, key)` 上的全序，与串行扫描所用比较器相同；
  因此把任意划分的局部 top-K 合并后，得到的仍是全局 top-K，且并列顺序一致。
- 每行的距离仍由同一函数在同一 FP 模式下计算，结果逐位相同。
- 量化筛选阈值取自**本切片**堆的最坏距离。切片堆比全局堆差（或相等），阈值因此更宽松，
  只可能多留候选，**不可能漏掉应入选的行**。这是本设计最关键的正确性点。
- 切片边界按 32 行对齐，尾部按 8/1 处理，不会跳过或重复任何一行。
- 已在 `tests/test_parallel_search.cpp` 中对 width ∈ {1,2,3,4,2}、12000 行、含大量等距
  记录的 48 条查询逐条比对序列化结果，并要求 width>1 时 worker 确实被启用。

## 5. 退化与回退

| 条件 | 行为 |
| --- | --- |
| 可用 CPU 只有 1 个 | `scan_width` 返回 1，走原串行路径，无额外开销（不建线程） |
| 候选行 < 1024 | 串行，避免唤醒成本 |
| worker 内抛异常 | 记录到 `exception_ptr`，主线程 join 后重抛，语义与串行一致 |
| 线程创建失败 | 未处理（`std::thread` 构造抛 `system_error`）；视为资源错误 |

## 6. 风险

1. **测量噪声**：本机共享、无隔离，同二进制对照的配对中位数噪声达 ±3%，单对波动 ±13%。
   因此验收要求多配对 + 胜率，而非单次数字。
2. **官方 CPU 配额未知**：设计按亲和性自适应；若官方只给 1 CPU，自动退化为串行。
3. **上下文切换**：2 worker + 主线程在 2 CPU cgroup 内竞争，池唤醒约 5–15 µs；
   查询量级 300–400 µs，占比可接受，但小查询由 1024 行阈值挡掉。
4. **二进制布局漂移**：新增代码改变了内联/对齐，可能对写路径产生与线程无关的微小偏移；
   用「同源码但关闭线程」的构建做对照来分离这一因素。

## 7. 验收门槛（事先固定）

- 确定性：width 1/2/3/4 结果逐字节相同；CI 测试覆盖。
- 回归：Release CTest 8/8、stress 21/21、optimization --large 16/16、public bridge 4/4、
  官方公开题包 20 用例/95 SQL。
- 性能：同机、2 CPU cgroup、独立数据目录、配对交替 ≥20 轮；
  查询配对中位数 ≥ +10% 且胜率 ≥ 75%；写入不得出现超出对照噪声的退化；
  峰值 RSS 变化 ≤ 2%。
- 环境：记录工具链、二进制 SHA-256、cgroup 配置。
