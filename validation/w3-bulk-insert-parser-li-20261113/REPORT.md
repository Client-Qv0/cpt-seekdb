# W3 — 批量 INSERT 专用解析

基线：W2 提交 `1d66388`。改动：`src/engine.cpp`（结构扫描 + `Engine::try_fast_insert`）、
`src/engine.hpp`（私有声明）、`src/row_codec.hpp`（文本级元组编码）、`tests/test_bulk_insert.cpp`。

## 机制

- 在 `Engine::execute` 调用 `parse_sql` 之前，先做一次**结构扫描**：匹配
  `INSERT INTO <表> [(列清单)] VALUES (...),(...)`，只记录每个元组在原始 SQL 中的字节区间。
  表名/列名只接受简单标识符，字符串只做边界跳过（含反斜杠转义与 `''` 双写），
  任何其它构造立即返回 false。
- 表元数据存在时，用 `codec::encode_tuple_text` 直接从 SQL 区间解析并编码：
  BIGINT 从原文本解析、VARCHAR 就地去转义、VECTOR 逐 float 写入目标缓冲。
- 不建立通用 `Token`/`Literal` AST，也不复制 1.3 KB 的向量文本。
- 只有**列清单与 schema 顺序一致**（含省略列清单）时才走快路径；其余回退通用解析器。
- 回退是严格的：编码器遇到反斜杠转义、非预期记号就抛 `FastInsertUnsupported`，
  `abort_statement()` 撤销后由通用解析器重新解析，绝不会留下部分行。

## 实测（正式 JSONL 入口，预生成输入，2 CPU cgroup）

| 轮次 | 写入中位 | 胜率 | 查询中位 | 胜率 | 峰值 RSS |
| --- | ---: | ---: | ---: | ---: | --- |
| 3 对 | +3.70% | 2/3 | +4.87% | 2/3 | 5376→5248 KiB |
| 5 对（最终二进制） | **−2.98%** | 2/5 | +0.09% | 3/5 | 5504→5248 KiB |

阶段耗时（插桩构建，写入阶段，总计 0.29–0.31 s）：
protocol（JSON 解码）0.053–0.058 s、**encode（解析+编码，并行）0.128–0.134 s**、
apply（查重+journal）0.023 s，其余约 0.09 s 为语句记账与落盘。

对比基线：`protocol` 0.043–0.046、`convert+pack` 0.100–0.106、`apply` 0.024，
其余约 0.128 s。即 W3 把「其余」压掉约 0.036 s，但 encode 段相应增加，
**总时间基本不变**。

## 结论

**未达 15% 目标。** 合并 8 对配对数据，写入中位在 ±4% 之间摆动，方向不一致，判定为持平。

原因（来自阶段数据）：写入侧的时间分布是「协议 JSON 解码 ~18% + 浮点解析/编码 ~43%
+ 应用持久化 8% + 其它 ~30%」。W3 消除的是通用 AST/Literal 的构造成本，而向量文本在
`Literal` 里本来就是一个字符串，浮点解析的绝对量没有减少；所以结构收益真实但很小。

## 语义验证

- CTest 11/11，含新增 `bulk_insert`：列清单顺序、`''` 双写、反斜杠回退、
  语句内重复主键失败后不留行、维度错误后不留行、带空格的向量字面量。
- 压力黑盒 21/21、优化/大输出 16/16、public bridge 4/4、官方公开题包 20 用例 95 SQL。
- 一个真实缺陷在集成时被抓到并修复：最初未处理反斜杠转义，导致含 `\"` 的 VARCHAR
  长度算错（`optimization_acceptance` 报错）。修复方式是对含反斜杠的语句整体回退。
