# 本轮实验约定与真实判断记录

日期：2026-11-09。范围：高基数短记录内存边界与同版本可追溯基线；不提交正式评测，不改变旧审计材料。

## 已发生的判断

1. 阅读上一轮 AUDIT.md、production-manifest.json、run-manifest.json，逐项校验当前生产输入和冻结可执行文件。12 项生产输入无差异；本轮基线是源码摘要 `42affed2e283c8710151931f6f419eee64210eda42245be6d357dc20ae520bb2`、Release 二进制 `747092fd68833b52ec80020e050d4586d443220f513d6b3d932ab3e25eea072f`，并已另外复制保存。它不是 Git 基础提交所包含的实现。
2. 先执行真实 128 MiB cgroup、2 CPU、swap=0 的有界诊断，再决定实现。记录数按 50k、100k、250k、500k、1m、2m 增长；单阶段 60 秒、单案例 180 秒；首次失败或归一化耗时超过首规模 3 倍后停止该类扩容。两类记录是 BIGINT 主键 + BIGINT 标量，以及再加 VECTOR(4) FP32。单个 INSERT 1000 行，显式回滚事务最多更新 25k 行。
3. 基线两类记录在 1m 均可完成所有诊断阶段。scalar 重启后的匿名内存从 50k 的 3,485,696 B 增至 1m 的 64,282,624 B，约 64 B/行。两类 2m 均完成全部写入及主键点查后，在首次扫描时被 Docker 明确标记 OOMKilled；保留失败记录与数据目录。不是只因 memory.peak 触顶就断言 OOM，也不是把峰值当成泄漏。
4. 布局检查支持上述斜率：当前 std::map 节点为 56 B，glibc 分配含块开销约 64 B。仅把 Ref 缩小使节点到 48 B，仍落在同一分配档位。查询缓存和排序缓冲有固定预算；首扫额外分配会让接近上限的主键映射越界，但不能单凭匿名内存差推断全部是仍存活的缓存对象，分配器也会保留页。
5. 已选择一项候选：共享 arena 的紧凑有序主键树。它保持 WAL 格式、CRC、必要同步和 checkpoint 发布顺序，不同时调整行缓存预算或加入 ANN。目标是降低逐行索引常数；依然 O(N)，且 arena 高水位可能保留到 Store 关闭。磁盘 B+tree 加有界缓存可进一步消除常驻全量索引边界，但事务叠加、故障恢复与原子发布改动更大，本轮不一并引入。

## 候选验收与比较约定（配对运行前记录）

- 基线与候选均按 Release、同一工具链构建，保持同一运行镜像、128 MiB/2 CPU/swap 0、相同 SQL/随机种子与输出消费。每次使用独立数据目录。
- 先重跑候选与改动有关的单元/事务/恢复检查；通过后冻结候选源码和二进制哈希，再进行性能与资源比较。若候选改变，之前结果保留但不归给新版本。
- 三组配对顺序为 B→C、C→B、B→C。覆盖既有 10k×128、1000 条 Top-10 查询（半数过滤），以及两类共同可完成的 1m 高基数负载。分别报告写入、进程首次读、预热后的读、重启到首条有效响应。后者包含启动及协议开销，不冒充纯 WAL 重放时间。
- 不执行全局 drop_caches；“首次”指进程/数据库缓存首次，不代表操作系统页缓存冷。跨容器重启后的既存页可能已归属父 cgroup，不能把重启容器的文件缓存计数解释为整机缓存占用。
- 独立参考计算和结果校验在数据库 cgroup 与计时区间之外；采样开销保留，不从耗时中人为扣除。报告每轮原始结果、中位数、范围和波动，不能只挑最快值。
- 主要收益判据是相同高基数场景匿名内存稳定下降、既有成功规模不退化，并观察有界扩容是否改善。若正确性/恢复失败，或候选在基线可完成规模出现新增 OOM，则拒绝该候选。若没有稳定内存收益则回退。若成对耗时中位数出现超过 10% 的退化，先识别波动或路径原因，不能隐去该项；若无法解释/解决则不宣称本轮整体优化成功。
- I/O 仅保留真实 cgroup io.stat 原始观测，注明共享 WSL 设备及回写归因限制；数据目录大小、输出长度不是物理 I/O。所有结论均不是官方分数。

本文件只记录本轮已发生的判断与事先定义的验收方法，不代表学生已经表达过这些理解，也不构造未发生的反馈。

## 第一候选的负结果与同一方案的精修

第一候选 V1 (`0fa875ff…ac392` / binary `6d9c0863…d3093`) 的 18 次配对全部通过，但不能称全面性能提升：scalar 1m 写入配对耗时中位约增加 7.8%，10k×128 热查询增加 6.9%；恢复到首响应在两类高基数场景退化超过 10%。原始 `paired-candidate-v1` 全部保留，没有筛除不利轮次。

独立恢复 helper 使用相同日志字节、相同资源限制，只包围 Store 构造计时；scalar 和 vector4 三组配对恢复退化中位约 11.67% 和 11.66%。scalar 用户态 CPU 从中位 0.627229 s 增至 0.825909 s。它是额外诊断，不代替生产二进制的端到端结果；预读和复制日志使其属于 OS 缓存已预热的恢复。

代码复核发现 set 的存在性搜索与插入搜索重复；overlay 的外层搜索、transfer 搜索和插入搜索也重复，每次取源树最小节点又多一次下降。这支持额外索引 CPU 工作的解释，但没有通过插桩证明每项开销占比。

因此只精修同一紧凑索引方案：复用查找产生的插入位置，合并时保存后继再摘除，直接由 transfer 完成新行或覆盖。节点仍为 32 B，WAL、同步、cache 预算与排序路径未改变。V2 独立冻结树摘要 `df56a37dcbae572b6283dfd4ee67cccc1e7e15f2117b59760cf7628936ae18f3`；V1 的所有源码、二进制、诊断、负收益继续保留。V2 必须重新完成回归、资源验证和 18 次配对，不能继承 V1 的通过结论。
