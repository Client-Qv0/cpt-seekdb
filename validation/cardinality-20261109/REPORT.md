## 瓶颈证据与方案取舍

真实 cgroup v2：`memory.max=134217728`（128 MiB），`memory.swap.max=0`，CPU quota 2 核。数据目录在 WSL ext4，驱动、参考计算和响应保存位于被测数据库 cgroup 外。

诊断规模为 50k、100k、250k、500k、1m、2m；每阶段上限 60 秒、每案例上限 180 秒。首次失败或归一化耗时显著退化后停止该类扩容。两类数据分别为 BIGINT 主键 + BIGINT 标量（原始字段 16 B/行），以及额外 VECTOR(4) FP32（原始字段共 32 B/行）；实际 WAL 含帧、表名和其他元数据，不能按原始字段宽度推断磁盘 I/O。主键顺序递增，标量和向量由固定周期公式产生，INSERT 每批 1000 行自动提交。

基线两类记录都能完成 1m 的全部阶段，但 2m 在全部写入获确认、33 次主键查询完成后，首次扫描被 Docker 确认 OOMKilled，退出码 137。精确失败阈值没有二分搜索，2m 只是本轮首个失败采样点；没有无限扩容。失败数据路径、事件采样和复现命令保存在 `baseline-boundary-notes.json`。个别被杀容器的最终 cgroup 已删除，最后存活样本中的 oom=0 不能覆盖 Docker 的 OOMKilled 事实，也没有补造消失后的计数。

基线 scalar 恢复后的匿名内存从 50k 的 3,485,696 B 增至 1m 的 64,282,624 B，斜率约 64 B/行。布局诊断发现 `std::map` 节点连分配档位开销约 64 B；仅缩小 Ref 后仍可能落在相同分配档位。首扫、预热、修改失效、再扫描的对照和有界缓存预算说明，常驻主键映射是随行数线性增长的主要压力，查询缓存不是唯一来源。匿名内存差值也不等于仍存活对象的精确大小，分配器和 arena 都可能保留已空闲页。

采用共享 arena 的紧凑有序树，把每个节点压至 32 B：保留主键、磁盘偏移、长度，使用 32 位节点索引和打包的父节点/颜色/墓碑位。不同事务层共享 arena，正常提交后的合并路径转移已有节点，无需新的 C++ 堆分配；这不代表 libc/内核内部操作或异常诊断也不分配。WAL 格式、CRC、fdatasync、checkpoint 原子发布及目录同步顺序保持不变；查询缓存预算、排序、FP32 和精确距离语义保持不变。

紧凑内存表示改动集中，能降低每行常数；磁盘 B+tree 配有界缓存可以进一步消除全量驻留索引，却需要更大范围的事务、缓存一致性和原子发布设计。本轮选择前者，**仍是 O(N) 索引内存，不是固定内存任意容量**。事务层、语句快照、恢复暂存会叠加；空闲槽复用而 arena 块保留到 Store 销毁。30 位节点编号还有理论容量上限，但实际内存边界更早到达。

没有引入 ANN。当前 CREATE INDEX 主要保存声明、查询仍走精确扫描/缓存，继续作为独立缺口。

## V1 的负结果与 V2 精修依据

V1 的 18 轮配对全部正确，但 scalar 1m 写入约慢 7.8%，10k×128 热查询约慢 6.9%；高基数重启到首响应慢于基线超过 10%。全部原始运行和分布在 `paired-candidate-v1`，不只展示有利轮次。

另用相同 WAL 字节、独立恢复 helper 直接计时 Store 构造。scalar 三组配对恢复耗时增加的中位数为 11.67%，vector4 为 11.66%；scalar 用户态 CPU 中位数从 0.627229 s 增至 0.825909 s。这反驳了“完全只是 Docker 启动噪声”的解释，但没有证明某个函数的精确占比。helper 的数据复制与 SHA 预读会预热 OS 缓存，且它是诊断可执行文件，不代替生产程序端到端计时。

代码复核发现额外树遍历：set 先查存在再查插入位置，overlay/transfer 又重复查目标树，每转移一个节点反复寻找源树最小值。V2 只精修同一方案：查找同时给出插入位置，保存后继再摘除，直接由 transfer 处理新增或覆盖。新增保存后继、重叠目标、极端主键和禁止分配测试。具体差异见 `candidate-v2-vs-v1.diff`；V1 的负结果不归给 V2，也没有被删改。

## 比较方法和解释边界

每种负载三组配对，顺序 B→C、C→B、B→C；每次独立数据目录，相同 SQL、seed、构建配置和输出消费。受控本地配对在 quota 2 CPU 外固定 CPU 0,1。单次容量诊断只固定 quota，因此它的耗时不用来宣称配对速度收益。

- 向量负载：seed 3179，10k×128D，100 行/批写入，1000 条 Top-10，其中过滤/无过滤各 500 条；单独记录进程首次查询和固定 10 次预热，随后计时完整 1000 查询。
- 高基数负载：两类各 1m；写入、首次和后续主键读、首扫及三次热扫、更新失效与复扫、删除/恢复、25k 行事务暂存与回滚/提交，以及重启后抽查。vector4 另做独立核对的过滤 Top-8。
- 不执行全局 drop_caches。“首次”仅表示该进程/数据库缓存首次，不表示 OS 页缓存冷。跨容器后既存页可能记在父 cgroup，不能把新容器 file 计数解释为整机缓存占用。
- 时间包含协议、JSON 编解码、管道消费和后台采样影响；启动到首响应包含 Docker 启动、恢复和首条响应，不是孤立 WAL 重放。
- memory.peak 是内核计数；anon/file/current 是采样值，其各自最大值未必同时发生。RSS 只作辅助。memory.events、memory.pressure 和 io.stat 原始值保留。
- 只有三组，且顺序并非完全均衡；结果是固定本地场景的证据，不是所有主键分布、维度、过滤比例或环境的保证。

## 独立正确性与恢复验证

10k×128D 性能 SQL 与冻结原性能生成器逐条比对后由真实数据库运行；高基数两类为本轮新增生成器，两版输入 SQL 哈希一致，不属于旧生成器逐条对照范围。参考计算在全部被测计时和数据库 cgroup 之外：从十进制 SQL 独立解析、先量化 FP32 再以 FP64 穷举欧氏距离；先过滤，再按距离与主键排序。逐条检查 ID 类型/合法范围、重复 ID、过滤谓词、TopK 集合与完整顺序、距离和 Recall，不只检查数量或排序。VECTOR(4) 使用独立 Python/heapq 的全量参考，不调用生产距离函数。

V2 原生 Release：CTest 5/5（紧凑树内部 7 套）、黑盒 19/19、额外回归 11/11；ASan/UBSan：CTest 5/5、常规黑盒 18 项通过且 1 项地址空间压力跳过、额外 8 项通过且大输出类 3 项跳过。ASan/UBSan 运行未报告错误；Release 未启用 sanitizer。跳过的大输出和压力在 Release 配置运行，不能说它们也通过 ASan。

覆盖语句原子性、失败语句不撤销此前事务工作、提交/回滚、随机参考模型、确认提交后 SIGKILL、未提交尾部、丢失提交响应、恢复过程终止，以及 checkpoint 写入/rename/目录同步边界。新增树测试覆盖随机 std::map 对照、两子节点删除、跨层转移、分配失败强保证、正常 finish_statement/commit 路径拦截 C++ new/new[] 分配等；没有拦截 libc/内核内部内存或 I/O 异常诊断的分配。双方交替读取 WAL 和 checkpoint 后全量核对 1000 初始行、999 修改后行及向量，双向通过。

这些是进程/文件边界验证，不等于真实断电、磁盘满或任意设备损坏验证。高基数性能场景恢复后仅做规定的有限 PK/标量核验，不是全量逐行恢复 oracle；4 维过滤向量查询在该性能工具中没有恢复后再次执行。另一个 1000 行兼容性用例才全量核对恢复后的向量。

## 尚未验证与等待官方题包

尚未验证：2m 以上的精确失败阈值；随机/恶意高基数输入的全部分布；任意大事务；真实断电、磁盘满和所有同步失败组合；OS 冷缓存性能；经校准的完整物理 I/O 归因；候选 Dockerfile 重新构建的产物一致性；真正 ANN；正式学习材料的评分。

等待官方题包：完整 stdin/stdout 协议、就绪/错误格式、正式 SQL/索引语义、MySQL 验收驱动、公开/隐藏恢复用例、官方资源和评分采样方式。当前 `--dev-protocol` 只用于本地，不宣称已满足官方提测条件。

物理 I/O 不能用数据库文件大小或 stdout 字节替代。io.stat 是真实 cgroup 原始观测，但共享 WSL ext4 设备、内核页缓存归属和延迟回写尚未校准，最终采样也不是全部回写清算，故不换算官方 I/O、分数或排名。

本组阶梯、事务、retention、恢复共 70 个受限容器均完成限额核验且没有 OOM。checkpoint_helper 阶段总耗时包含启动和恢复，detail.checkpoint_query_seconds 单独记录 CHECKPOINT 请求响应耗时；该助手编译选项为双方一致的 -O2；恢复助手使用 -O3，两者均单独绑定哈希，不混作生产 Release 的性能。

## 单行更新退化的补充对照

原 vector4 三次“更新加点查”一致变慢，前后 io.stat 观测均增加 4096 B/1 次 wio，内存压力计数无该阶段内增长；原适配器没有 cpu.stat，不能补造。后台采样起始时间戳也不足以证明 Python GIL 是原因。

额外执行 12 次固定对照（sampler 开/关各三对，每次五组相同前置扫描及向量查询后更新）。只改变测试侧后台采样，生产默认配置和二进制不变。每条 SQL 单独计时，CPU/压力/IO 捕获和真值检查在其计时外；它的“UPDATE+SELECT”合计排除了中间捕获间隙，与原连续阶段计时不同。每次从同一 WAL 独立复制后恢复，不能完全重现原来写入后的分配器和文件缓存历史。

12/12 通过，但 UPDATE 单条配对 B/C 中位及范围为：采样开 0.9547（0.5540–1.2169），采样关 1.0308（0.9819–2.0427）。方向和波动均不稳定，关闭采样没有稳定消除慢例；60 次 UPDATE 的短窗口 usage_usec 增量 77–355、nr_throttled 增量全为 0，也不能据此归因到某个系统调用或 GIL。**原三轮更新退化的原因仍未知。** 原负结果未删除，也未被这组控制替换。全部原值、适配说明与局限见 [更新延迟调查](update-latency-control-v2/ANALYSIS.md)。诊断已按预定次数结束，不追加挑选有利样本。

## 最终决定与三类结论

**保留精修版 V2 的内存优化，V1 仅留作有明确退化的实验记录。** 依据是两类 1m 的匿名内存收益在三组配对稳定出现、成功采样规模扩大至两类 2m、原有成功规模未出现新增 OOM、相关功能/事务/恢复回归全部通过，且 V1 的明显恢复退化已在 V2 受控配对和独立恢复诊断中消除。正常提交和恢复的持久性要求没有削弱。

这是有明确延迟取舍的内存优化：保留写入约 1%–2% 退化，以及原单行更新约 6→13 ms、原因未明的负结果；**不宣称全面提速或整体性能无回归**。新的 file 占用和原始 I/O 已披露；未发现本轮已测正确性、OOM 或内存资源回归，但没有据此保证所有输入、系统与资源指标均无退化。

- **已经实测**：精确版本绑定；B/V1/V2 的受控比较；V2 18 次配对、6066 组独立 128D 结果；12 项容量阶梯、三档事务、回滚高水位、checkpoint 与恢复；原生 Release/ASan 对应回归；4 项 cgroup 大输出/存储回归；12 次采样开关对照。各自实际范围和跳过项以本文和绑定日志为准。
- **尚未验证**：原写入后单行更新慢例的原因；超过 2m 的精确容量边界；任意规模事务及其他数据分布；真实断电/介质错误；OS 冷缓存；校准后的完整物理 I/O；真正 ANN；新的 Dockerfile 从头构建与官方学习材料评分。不能从本地结果推出这些结论。
